# 跨平台自动化架构与 Windows 后续规划

## 目标与边界

任务业务逻辑只实现一次，同时供 macOS 和后续 Windows 使用。平台层只负责窗口、截图、输入、坐标映射、等待/取消和系统诊断，不复制任务流程、页面判定或安全策略。

当前阶段只在已有 macOS 环境中完成抽象和回归，不实现或猜测 Windows 适配器。Windows 开发必须等具备真实 Windows 机器、真实游戏窗口和可重复截图后开始。

## 目标依赖方向

```text
Task Workflow
  ├─ 宝图、运镖、师门、秘境等业务状态
  └─ Action 的排列、分支、上限和终态
              ↓
Domain Action / Recognition
  ├─ 打开活动、切换日常、滚动、参加任务
  ├─ 任务专属语义动作
  └─ 页面证据与风险分支判定
              ↓
Platform-neutral Contracts
  ├─ SceneSource / ActionScene
  ├─ ActionInput / ActionWaiter
  ├─ EventSink / WorkflowResult
  └─ Geometry / calibration contract
              ↓
Platform Adapter
  ├─ macOSAdapter
  └─ WindowsAdapter（后续）
```

依赖只能向下。Workflow 和 Action 不得导入 macOS/Windows 控制器、窗口句柄类型或系统 API。

## 当前实施阶段

### 阶段 1：平台无关 Action（已完成首批）

- 已建立场景、输入、等待、事件、结果和输入预算协议。
- 已抽取通用几何与日常活动领域动作。
- 已提供两种点击语义：优先点击当前截图中的识别框；固定控件可使用经过识别状态门控的相对坐标点击，并按实时 `image_size` 缩放。
- 宝图、普通运镖、师门、秘境降妖、福利签到、帮派签到、考古、三界奇缘和科举已使用平台无关 Action，macOS 运行时作为当前输入适配器。
- 答题动作只接收当前 Scene、稳定题目 key、答案标识和识别坐标；题库、OCR、模型与平台输入均不进入 Action。

### 阶段 2：平台无关 Workflow（现有十项已完成）

- 已建立 `WorkflowContext`、`SceneSource`、`WorkflowResult` 和只读检查结果契约。
- 宝图、普通运镖、师门、秘境降妖、福利签到、帮派签到、考古、三界奇缘和科举的任务循环、业务阶段、动作组合、终态和计数已从 `run_*_macos.py` 移入平台无关 Workflow。
- 十个 macOS 启动器现在只保留参数解析、识别源与 macOS 适配器创建、信号处理和控制台协议输出。
- 识别器作为 Workflow 依赖注入，平台视觉差异不得写入任务状态机。
- 秘境继续复用打开活动、切换日常、活动列表滚动和识别框点击动作；活动导航共享 16 次输入预算，任务推进保留战斗上限、等待上限、未知画面上限、重复序列保护和资产分支零输入停止。
- 福利刮卡已抽成有界多拖动 Action；帮派签到、分红及确认分别保持一次性保护；考古保留一次洛阳铲购买上限、10 次挖掘目标和逐动作预算。
- 三界奇缘与科举共用 `AnswerOptionClickAction`；科举同题等待、最终题计数和三界多选状态分别由任务 Workflow 管理。三界的活动入口、日常页签、活动列表滚动和参加任务也已组合为平台无关导航 Workflow。
- 捉鬼的组队、招募、目标等级拖动、阵法、钟馗导航、战斗等待和精确轮次状态已迁入 `ZhuoguiWorkflow`；场景分类移入平台无关识别模块，旧模块只保留兼容导出。
- 现有有输入任务的 Action/Workflow 迁移已完成；只读日程采集不产生输入，无需迁移动作。下一阶段按用户安排统一执行 macOS 实机矩阵，不在本轮逐项启动游戏。
- 当前阶段只完成离线适配，不逐项执行实机验证；待现有功能全部迁移后统一进行 macOS 实机矩阵验收。

验收证据：宝图、秘境、福利签到、帮派签到、考古、三界导航/答题、科举和捉鬼 Workflow 已在两个独立内存适配器上得到相同动作序列、等待序列和结构化结果；只读检查均为零输入。十个平台启动器已不包含任务输入循环。危险分支、战斗计数、购买上限、刮卡轨迹、多选计数、同题等待、等级拖动、精确轮次和重复保护继续由离线回归覆盖，统一实机验收后置。

### 阶段 3：macOS 适配器收口（统一 backend 与坐标预览首批完成）

- macOS 截图与原生输入已移入独立平台适配模块，通用 runtime 不再依赖任务 runner。
- 已建立截图签名，记录截图来源、输出尺寸、原始尺寸、内容裁剪区和像素倍率；系统 fallback 即使统一输出 `1020×718`，原始窗口尺寸变化仍会使旧签名失效。
- 已完成截图来源切换、窗口尺寸变化、旧 Scene 和缺失签名的零输入门控，并输出首次锁定的结构化诊断事件。
- `MacOSTaskRuntime` 已依赖统一 `MacOSWindowBackend`；输入 Scene 携带产生识别结果的原始帧，点击/拖动使用实时内容矩形映射，固定 28 点标题栏路径不再用于已迁移任务。
- 输入和只读预测前都会重新读取窗口 PID 与几何：移动窗口只更新原点，resize、PID 或 frame ID 变化会使旧帧失效并保持零输入。
- 预检证据已包含窗口边界、内容矩形、缩放、frame ID；有识别框时额外输出框中心像素和预测屏幕点，无框时不产生预测点。四锚点完成前明确标记 `anchorValidation: pending`。
- 2026-07-30 只读实机探测在窗口 `6637` 取得 Maa `923×720` 帧，窗口为 `1051×820` 点、缩放 `0.8782112274`；宝图预检因当前位于秘境页返回 `unknown`，全程零输入。
- 待实机完成无遮挡主界面四锚点、Retina/显示缩放和第二种窗口尺寸的预测点验收。
- 在至少两种窗口尺寸下对通用 Action 和首批 Workflow 做实机回归。

### 阶段 4：任务资源收益编排（平台无关契约首批完成）

- 建立平台无关 `ResourceSnapshotWorkflow`，统一采集等级、经验、金币和银币；各任务 Workflow 不自行打开资源页面。
- 控制台按 `执行前快照 -> 任务 -> 执行后快照 -> 净变化` 编排，并把快照关联到精确 `run_id` 和 `targetId`。
- 取消、安全停止、窗口失效后保持零输入；结束快照缺失只影响收益状态，不篡改任务结果。
- 跨等级或存在人工/后台干扰时降低归因可信度，不把观察到的净变化宣称为奖励总额。
- 完整设计与 R0-R5 实施顺序见 [任务资源收益统计规划](task-resource-yield-plan.md)。

当前证据：平台无关快照、字段证据和差值计算器已实现，覆盖经验跨等级、部分数据、负净变化、身份变化和外部干预；平台资源采集 Workflow、存储和生命周期编排尚未接入。

## Windows 后续开发规划（具备 Windows 机器后启动）

### W0：环境取证与技术选型

- 确认运行目标：Windows 原生客户端、模拟器或其他包装形式，不预先假设与 macOS 窗口结构一致。
- 记录系统版本、DPI 缩放、显示器布局、窗口模式、游戏内容尺寸和进程/窗口标识。
- 验证 MaaFramework 可用的 Windows 截图与输入方式，分别采集窗口化、移动窗口和不同 DPI 的原始截图。
- 建立最小诊断程序，只允许截图、显示窗口信息和预览预测点击点，不发送游戏输入。

完成门槛：可以稳定绑定唯一目标窗口并获取未拉伸的游戏内容截图；已选定输入方式且不依赖硬编码窗口边框。

### W1：Windows 平台适配器

- 实现与 macOS 相同的 `SceneSource`、`ActionInput` 和 `ActionWaiter` 协议。
- 封装窗口发现、精确绑定、截图、点击、拖动、取消屏障和结构化输入日志。
- 平台适配器接收截图坐标，只在内部映射为 Windows 屏幕/客户区坐标。
- 不在 Workflow 或 Action 中添加 `if windows` 分支。

完成门槛：平台无关契约测试全部复用；同一目标上的截图和输入始终绑定同一窗口，停止确认后不再输入。

### W2：DPI 与窗口标定

- 使用 Windows 客户区 API 和真实截图确定内容矩形，不复用 macOS 标题栏常量。
- 覆盖 100%、125%、150% 等实际可用 DPI；区分逻辑坐标、物理像素和截图像素。
- 用至少四个稳定视觉锚点验证缩放、偏移和宽高比；不满足阈值时阻止任务。
- 移动窗口不应要求重标定，改变内容尺寸、DPI 或截图方式必须使旧标定失效。

完成门槛：两种窗口尺寸和至少两档实际 DPI 下，预测点与真实控件一致；错误标定零输入。

### W3：通用动作冒烟验证

- 按“只读场景 → 打开活动 → 日常页签 → 小步滚动 → 关闭页面”顺序验证。
- 每个 Action 分别核对前置证据、一次输入、后置页面、重复保护、取消和日志。
- 先验证无资产风险动作，不执行购买、出售、消耗、复活或批量操作。

完成门槛：通用动作无需修改即可使用 Windows 适配器；若动作语义有问题，修复后 macOS 与 Windows 共同继承。

### W4：任务兼容矩阵

- 按宝图、普通运镖、师门、签到、秘境、答题、捉鬼的顺序逐项启用。
- 每项分别记录离线契约、Windows 单次实机、连续两轮、主动停止和异常页面结果。
- 平台视觉差异使用资源配置或识别策略注入，不复制整套 Workflow。
- 复用平台无关资源快照和差值计算契约；Windows 只新增资源页面识别资产和适配器实机验证。

完成门槛：任务通过矩阵后才加入 Windows 白名单；未验证任务明确显示为不支持。

### W5：控制台、诊断与发布

- 控制台根据目标平台创建对应适配器，并展示平台、窗口、DPI、标定和权限状态。
- 诊断包记录脱敏截图、内容矩形、坐标变换、Action/Workflow 结果和版本信息。
- 在干净 Windows 环境验证安装、启动、停止、升级和回滚。

完成门槛：非开发环境可重复运行已通过矩阵的任务，常见 DPI、权限和窗口错误有直接处理建议。

## 跨平台约束

- 不通过复制 `run_*_windows.py` 业务循环实现 Windows 支持；平台入口只能注入适配器。
- 不共享未经验证的平台常量，例如标题栏高度、窗口边框、DPI 比例或截图裁剪值。
- OCR/模板的业务含义共享，平台专属视觉资源通过资源包注入。
- 所有正式输入必须经过 Action、取消守卫、输入预算和结构化日志。
- Windows 实机证据完成前，状态只能标记为“已规划”或“离线契约验证”，不能标记为支持。
